# Independent code audit (2026-09-18) -- findings and response

An independent code audit of this repository at commit `b3c17db` found two
P0 bugs in the offline simulators, two P0 gaps in the (already NOT_RUN)
MQL4 code, and several P1 issues. Every P0 finding was reproduced
independently in this session before being fixed. This document records
what was found, how it was verified, and what changed.

## Conclusion up front

The audit's own conclusion was correct: **the previously-reported strategy
results could not be trusted for strategy selection until the simulator
bugs were fixed.** They have been fixed and every affected number has been
recomputed (see `reports/README.md` for old vs. new). The fixes did **not**
change the qualitative outcome -- all three strategies tried are still net
negative on the only available sample -- but the exact figures did change,
sometimes materially (see the table below).

## P0-1: entry candle's own SL/TP was never checked (FIXED, both simulators)

**Finding:** in both `simulator.py` (London breakout) and
`simulator_ema_cross.py` (EMA crossover / Bollinger reversion), a new
position opened at a bar's open was never checked against that SAME bar's
own high/low. The exit-processing block for a timestamp ran BEFORE that
timestamp's new entries were opened, so the position didn't exist yet when
its own bar was checked; the next check only happened on the FOLLOWING bar.
A same-bar SL touch was therefore silently skipped and only caught, much
worse, as a "gap" exit on the next bar's open.

**Independent reproduction:** a synthetic BUY at 1.10000 (spread 0.00010),
SL 1.09900, where the entry candle's own low reaches 1.09000. Before the
fix: exit as `SL_GAP` at 1.09000, net -223.30 USD. After the fix: exit as
`SL` at 1.09900 (the actual SL level), net -25.30 USD -- matching the
audit's own independently-computed expected value.

**Fix:** both simulators now track positions opened within the current
timestamp and immediately check them against that same bar before moving
to the next timestamp. Regression tests:
`python/tests/test_simulator_ema_cross_regressions.py::test_entry_bar_sl_checked_not_skipped_to_next_bar_gap`
and `python/tests/test_simulator_regressions.py` (a whole-real-data
invariant check, since `simulator.py` has no injectable signal engine for
a small synthetic repro).

## P0-2: configured portfolio/correlated-group risk caps were not enforced in the H1 simulator (FIXED)

**Finding:** `simulator_ema_cross.py` (used by the EMA-crossover and
Bollinger strategies) never called `account_risk.new_idea_within_risk_caps`
-- only the account-floor check ran. `max_concurrent_risk_usd` and
`correlated_group_max_risk_usd` therefore had no effect regardless of
value. (`simulator.py`, the London breakout, already called this function
correctly -- this gap was specific to the H1 simulator module.)

**Independent reproduction:** setting both caps to 0.0 in config, the
EMA-crossover run still opened and closed trades exactly as before --
proving the caps did nothing.

**Fix:** `simulator_ema_cross.py` now builds the same
`open_risk_by_idea`/`idea_symbol`/`idea_bucket` structures as
`simulator.py` and calls `new_idea_within_risk_caps` before opening any
position, skipping with reason `CORRELATED_OR_PORTFOLIO_RISK_CAP` when it
fails. Regression tests: `test_portfolio_cap_zero_blocks_all_entries`,
`test_correlated_group_cap_blocks_second_same_direction_symbol`.

## P0-3 / P0-4: MQL4 unprotected-position and stop-retry gaps (fixed structurally, still NOT_RUN)

Neither of these could be executed or tested -- no MetaEditor/MT4 was
available in this environment, same as every other MQL4 claim in this
project. The fixes below are structural corrections based on re-reading the
code and MQL4 documentation, not verified runs.

- **`OrderExec.mqh`, `OpenMarketOrderWithRetry`:** a failed `OrderModify`
  (applying SL/TP after a market order opened with SL=0/TP=0) used to just
  log and return the ticket anyway, with no actual retry mechanism despite
  the log message claiming one. Fixed: bounded immediate retry, then close
  the position rather than return an unprotected one.
- **`FTMO_Swing_EA_EmaCross.mq4` / `FTMO_Swing_EA.mq4`, `OnTick`:** the
  risk-stop closure was gated on `StopActive && !wasStopped` -- only the
  tick the stop first triggered. A failed close was never retried on a
  later tick despite the log message promising a retry. Fixed: retries
  every tick while the stop is active and anything is still open.
- **`Persistence.mqh` (found independently while investigating the above,
  not in the audit's own list, but the audit's point 6 said this file
  "needs to be verified and fixed"):** the state-file read logic
  concatenated `FileReadString` results with no separator (each call
  already strips the line terminator) and then split on `'\n'` -- which
  could never find more than one element, so `LoadRiskState` reported
  "corrupt state file" and returned `false` on every read after the very
  first save. Since the EA's `OnInit` refuses to start when `LoadRiskState`
  fails, this would have broken every restart. Fixed: the whole state is
  now one `|`-delimited line, read and written with a single call each way;
  renamed the file away from the misleading `.json` extension (it was
  always positional plain text, never real JSON).
- **`CloseAllManagedPositionsAndPendings` renamed to
  `CloseAllPositionsAndPendingsAccountWide`, and no longer filtered by
  `MagicNumber`:** the audit noted the spec requires monitoring "the whole
  account, not just the EA's MagicNumber," and this design assumes a
  dedicated account. If a foreign position is what pushed equity into the
  stop, closing only this EA's own orders would leave that foreign position
  open and defeat the point of the stop. The account-wide *scan*
  (`AccountRisk.mqh`) was already correct; the *closing* action is now
  account-wide too.
- **Pending-order risk (not counted, still 0 in the pre-trade check):**
  documented as intentional for this design -- neither strategy ever places
  a pending order. Flagged in `AccountRisk.mqh` as needing revisiting if a
  future strategy introduces pending orders.

## P1-5: swap was not modeled (FIXED, approximation)

**Finding:** neither simulator accrued swap for positions held overnight
-- material for `strategy_ema_cross.py`, which is designed to hold across
the session-close boundary.

**Fix:** `simulator_ema_cross.py` now accrues swap once per FTMO-day
rollover for every open position, using the confirmed
`swap_long_points`/`swap_short_points`/`triple_swap_weekday` instrument
spec, tripled on the night starting Wednesday. This is an approximation,
not a confirmed model: the real MT4 rollover hour (and whether it lines up
with the Prague-day boundary used here) is unconfirmed -- see
`docs/UNKNOWNS.md`. It is a materially better approximation than the
previous silent zero. Regression tests:
`test_swap_usd_matches_hand_computed_value`,
`test_swap_accrues_once_per_night_held_and_triples_on_wednesday`.

The audit's related point -- that commission is not included in the 25 USD
risk-per-idea sizing budget, so true risk is slightly above the nominal
figure -- is accepted as a known, small (order of a few dollars on a 25 USD
budget) approximation and was not changed; re-deriving lot size net of
commission would need an iterative or closed-form adjustment to
`lots_for_risk` that was judged lower priority than the P0/P0-adjacent
items above.

## P1-6: restart / instance-guard honesty (partially addressed)

The audit correctly noted that the account/server match check in
`RiskState._check_instance_guard` / MQL4's `LoadRiskState` is not an
exclusive lock -- it accepts a legitimate restart of the same controller
and a second concurrent instance identically, since both present the same
account/server. This is a real, accepted limitation: implementing a true
exclusive lock (e.g. a lock file with a liveness heartbeat) was judged out
of scope for this round of fixes, given it cannot be verified without a
real MT4 terminal anyway. The severe, independently-reproducible bug in the
same file (the read-format bug above) has been fixed; the weaker
instance-guard claim is now documented accurately (see
`docs/UNKNOWNS.md`) rather than overstated.

## P1-7: end-of-sample reporting (FIXED)

**Finding:** the simulators returned only realized `final_balance`, with no
visibility into positions still open when the sample ran out, and no
separate accounting for floating P/L.

**Fix:** both `SimulationResult` and `EmaCrossResult` now expose
`open_positions_at_end` and `final_equity` (the last equity-curve point).
`run_ema_cross.py`'s report prints both the realized-balance net and the
final-equity net, and how many positions (if any) were still open. In the
actual runs on the supplied data, both strategies end with 0 open
positions, so this did not change any reported number here, but it is no
longer silently unverified.

## P1-8: the statistics section overstated its own certainty (rewording, no code change)

**Finding:** the earlier wording ("a 38% hit rate ... is exactly what
chance alone would produce") asserted more than the sweep alone
establishes -- there was no formal null model, no correction for the
strategies' shared risk-management and cost structure, and no dependency-
aware resampling. The audit is right that this doesn't prove the positive
results are noise, any more than the short sample proves the strategies
can't work.

**Fix:** `README.md` and `FULL_REPORT.md` are reworded to claim only what
the sweep actually shows -- that a substantial fraction of arbitrary
parameter choices looked positive on this fixed sample, which is a reason
for caution, not a formal proof of anything -- and to note explicitly that
a rigorous answer would need a proper permutation/null-model test (already
suggested as a next step in `docs/HANDOFF_STRATEGY_SEARCH.md` and
`docs/FULL_REPORT.md`, unchanged by this audit).
