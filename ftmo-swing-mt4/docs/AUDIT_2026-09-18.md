# Independent code audit (2026-09-18) -- findings and response

An independent code audit of this repository at commit `b3c17db` found two
P0 bugs in the offline simulators, two P0 gaps in the (already NOT_RUN)
MQL4 code, and several P1 issues. Every P0 finding was reproduced
independently in this session before being fixed. This document records
what was found, how it was verified, and what changed.

## Conclusion up front

The audit's own conclusion was correct: **the previously-reported strategy
results could not be trusted for strategy selection until the simulator
bugs were fixed.** They have been fixed and every affected number has been
recomputed (see `reports/README.md` for old vs. new). The fixes did **not**
change the qualitative outcome -- all three strategies tried are still net
negative on the only available sample -- but the exact figures did change,
sometimes materially (see the table below).

## P0-1: entry candle's own SL/TP was never checked (FIXED, both simulators)

**Finding:** in both `simulator.py` (London breakout) and
`simulator_ema_cross.py` (EMA crossover / Bollinger reversion), a new
position opened at a bar's open was never checked against that SAME bar's
own high/low. The exit-processing block for a timestamp ran BEFORE that
timestamp's new entries were opened, so the position didn't exist yet when
its own bar was checked; the next check only happened on the FOLLOWING bar.
A same-bar SL touch was therefore silently skipped and only caught, much
worse, as a "gap" exit on the next bar's open.

**Independent reproduction:** a synthetic BUY at 1.10000 (spread 0.00010),
SL 1.09900, where the entry candle's own low reaches 1.09000. Before the
fix: exit as `SL_GAP` at 1.09000, net -223.30 USD. After the fix: exit as
`SL` at 1.09900 (the actual SL level), net -25.30 USD -- matching the
audit's own independently-computed expected value.

**Fix:** both simulators now track positions opened within the current
timestamp and immediately check them against that same bar before moving
to the next timestamp. Regression tests:
`python/tests/test_simulator_ema_cross_regressions.py::test_entry_bar_sl_checked_not_skipped_to_next_bar_gap`
and `python/tests/test_simulator_regressions.py` (a whole-real-data
invariant check, since `simulator.py` has no injectable signal engine for
a small synthetic repro).

## P0-2: configured portfolio/correlated-group risk caps were not enforced in the H1 simulator (FIXED)

**Finding:** `simulator_ema_cross.py` (used by the EMA-crossover and
Bollinger strategies) never called `account_risk.new_idea_within_risk_caps`
-- only the account-floor check ran. `max_concurrent_risk_usd` and
`correlated_group_max_risk_usd` therefore had no effect regardless of
value. (`simulator.py`, the London breakout, already called this function
correctly -- this gap was specific to the H1 simulator module.)

**Independent reproduction:** setting both caps to 0.0 in config, the
EMA-crossover run still opened and closed trades exactly as before --
proving the caps did nothing.

**Fix:** `simulator_ema_cross.py` now builds the same
`open_risk_by_idea`/`idea_symbol`/`idea_bucket` structures as
`simulator.py` and calls `new_idea_within_risk_caps` before opening any
position, skipping with reason `CORRELATED_OR_PORTFOLIO_RISK_CAP` when it
fails. Regression tests: `test_portfolio_cap_zero_blocks_all_entries`,
`test_correlated_group_cap_blocks_second_same_direction_symbol`.

## P0-3 / P0-4: MQL4 unprotected-position and stop-retry gaps (fixed structurally, still NOT_RUN)

Neither of these could be executed or tested -- no MetaEditor/MT4 was
available in this environment, same as every other MQL4 claim in this
project. The fixes below are structural corrections based on re-reading the
code and MQL4 documentation, not verified runs.

- **`OrderExec.mqh`, `OpenMarketOrderWithRetry`:** a failed `OrderModify`
  (applying SL/TP after a market order opened with SL=0/TP=0) used to just
  log and return the ticket anyway, with no actual retry mechanism despite
  the log message claiming one. Fixed: bounded immediate retry, then close
  the position rather than return an unprotected one.
- **`FTMO_Swing_EA_EmaCross.mq4` / `FTMO_Swing_EA.mq4`, `OnTick`:** the
  risk-stop closure was gated on `StopActive && !wasStopped` -- only the
  tick the stop first triggered. A failed close was never retried on a
  later tick despite the log message promising a retry. Fixed: retries
  every tick while the stop is active and anything is still open.
- **`Persistence.mqh` (found independently while investigating the above,
  not in the audit's own list, but the audit's point 6 said this file
  "needs to be verified and fixed"):** the state-file read logic
  concatenated `FileReadString` results with no separator (each call
  already strips the line terminator) and then split on `'\n'` -- which
  could never find more than one element, so `LoadRiskState` reported
  "corrupt state file" and returned `false` on every read after the very
  first save. Since the EA's `OnInit` refuses to start when `LoadRiskState`
  fails, this would have broken every restart. Fixed: the whole state is
  now one `|`-delimited line, read and written with a single call each way;
  renamed the file away from the misleading `.json` extension (it was
  always positional plain text, never real JSON).
- **`CloseAllManagedPositionsAndPendings` renamed to
  `CloseAllPositionsAndPendingsAccountWide`, and no longer filtered by
  `MagicNumber`:** the audit noted the spec requires monitoring "the whole
  account, not just the EA's MagicNumber," and this design assumes a
  dedicated account. If a foreign position is what pushed equity into the
  stop, closing only this EA's own orders would leave that foreign position
  open and defeat the point of the stop. The account-wide *scan*
  (`AccountRisk.mqh`) was already correct; the *closing* action is now
  account-wide too.
- **Pending-order risk (not counted, still 0 in the pre-trade check):**
  documented as intentional for this design -- neither strategy ever places
  a pending order. Flagged in `AccountRisk.mqh` as needing revisiting if a
  future strategy introduces pending orders.

## P1-5: swap was not modeled (FIXED, approximation)

**Finding:** neither simulator accrued swap for positions held overnight
-- material for `strategy_ema_cross.py`, which is designed to hold across
the session-close boundary.

**Fix:** `simulator_ema_cross.py` now accrues swap once per FTMO-day
rollover for every open position, using the confirmed
`swap_long_points`/`swap_short_points`/`triple_swap_weekday` instrument
spec, tripled on the night starting Wednesday. This is an approximation,
not a confirmed model: the real MT4 rollover hour (and whether it lines up
with the Prague-day boundary used here) is unconfirmed -- see
`docs/UNKNOWNS.md`. It is a materially better approximation than the
previous silent zero. Regression tests:
`test_swap_usd_matches_hand_computed_value`,
`test_swap_accrues_once_per_night_held_and_triples_on_wednesday`.

~~The audit's related point -- that commission is not included in the 25 USD
risk-per-idea sizing budget... was not changed~~ -- **SUPERSEDED by the
follow-up round below (2026-09-18, continued): this was fixed.**
`lots_for_risk`/`risk_usd_for_lots` gained `extra_cost_usd_per_lot`, folding
commission directly into the same 25 USD budget the SL distance is sized
against, in both Python simulators and the MQL4 `SymbolSpec.mqh`. The
effect on this sample was NOT small: for trades with a tight SL distance,
lot size dropped materially (one real GBPUSD trade went from 3.78 to 2.15
lots), moving the baseline result from -446.71 to -319.38 USD and the EMA
crossover from -296.65 to -281.89 USD. See the follow-up section for the
full account.

## P1-6: restart / instance-guard honesty (partially addressed; further closed in the follow-up round below)

The audit correctly noted that the account/server match check in
`RiskState._check_instance_guard` / MQL4's `LoadRiskState` is not an
exclusive lock -- it accepts a legitimate restart of the same controller
and a second concurrent instance identically, since both present the same
account/server. The severe, independently-reproducible bug in the same
file (the read-format bug above) was fixed in this round; the weaker
instance-guard claim was, at the time, documented accurately (see
`docs/UNKNOWNS.md`) rather than fixed. **UPDATE (follow-up round below):
`Persistence.mqh` now has a real exclusive-open lock file
(`AcquireInstanceLock`/`ReleaseInstanceLock`), closing this for the
in-scope case (two EA instances in the same terminal/account). It still
cannot close the cross-terminal case (a second, separate MT4 installation)
-- see the follow-up section's "remaining open items."**

## P1-7: end-of-sample reporting (FIXED)

**Finding:** the simulators returned only realized `final_balance`, with no
visibility into positions still open when the sample ran out, and no
separate accounting for floating P/L.

**Fix:** both `SimulationResult` and `EmaCrossResult` now expose
`open_positions_at_end` and `final_equity` (the last equity-curve point).
`run_ema_cross.py`'s report prints both the realized-balance net and the
final-equity net, and how many positions (if any) were still open. In the
actual runs on the supplied data, both strategies end with 0 open
positions, so this did not change any reported number here, but it is no
longer silently unverified.

## P1-8: the statistics section overstated its own certainty (rewording, no code change)

**Finding:** the earlier wording ("a 38% hit rate ... is exactly what
chance alone would produce") asserted more than the sweep alone
establishes -- there was no formal null model, no correction for the
strategies' shared risk-management and cost structure, and no dependency-
aware resampling. The audit is right that this doesn't prove the positive
results are noise, any more than the short sample proves the strategies
can't work.

**Fix:** `README.md` and `FULL_REPORT.md` are reworded to claim only what
the sweep actually shows -- that a substantial fraction of arbitrary
parameter choices looked positive on this fixed sample, which is a reason
for caution, not a formal proof of anything -- and to note explicitly that
a rigorous answer would need a proper permutation/null-model test (already
suggested as a next step in `docs/HANDOFF_STRATEGY_SEARCH.md` and
`docs/FULL_REPORT.md`, unchanged by this audit).

## Section 4.1: cross-symbol same-tick causality leak (FIXED)

**Finding:** in both `simulator.py` and `simulator_ema_cross.py`, the
"remaining risk" contributed by an ALREADY-open position to a
SIMULTANEOUS other-symbol entry's portfolio/correlated-cap check was
computed from that position's CURRENT BAR'S CLOSE -- but if that position
was itself opened on THIS SAME timestamp (a same-tick entry on both
symbols), its own bar's close is a value only knowable LATER within the
same minute, and using it leaks later-in-the-bar information into the
other symbol's entry decision at the identical instant.

**Independent reproduction:** held EURUSD's entry-minute OPEN (and
therefore its actual fill price) fixed, varied only its entry-minute
CLOSE -- GBPUSD's simultaneous entry outcome (accepted/rejected, and
which skip reason) changed depending on a value that should have been
irrelevant to it. Confirmed the leak exists before fixing it.

**Fix:** a position opened on the SAME timestamp as the check now
contributes its full originally-sized risk (`risk_usd_at_entry`) instead
of a close-derived mark. Verified the fix eliminates the discrepancy;
regression test:
`test_same_tick_entry_risk_view_ignores_other_symbols_own_entry_bar_close`.
Did not change any previously-reported real-dataset number (the
triggering condition never occurred in the actual ~2-month sample).

## Section 4.3: end-of-run equity/balance mismatch (FIXED)

**Finding:** the equity-curve point recorded for a timestamp was appended
BEFORE that timestamp's own entries/same-bar closures, so a trade opened
AND closed within the very LAST timestamp of a run updated
`final_balance` but not the already-recorded last equity-curve point.
`final_equity` (drawn from that point) could come back stale (e.g. still
the untouched initial balance) while `final_balance` correctly reflected
the loss.

**Independent reproduction:** exact repro matching the cited numbers --
`balance=9974.70, open_positions=0, final_equity=10000` before the fix.

**Fix:** the equity-curve append moved to AFTER that timestamp's own
entries and same-bar closures, using a freshly recomputed "settled"
floating P/L (`_floating_pnl()`), in both simulators. Verified:
`final_balance == final_equity` exactly whenever nothing is left open.
Regression test:
`test_final_equity_matches_final_balance_when_last_tick_closes_last_position`.
Did not change any previously-reported real-dataset number.

## Commission folded into the 25 USD sizing budget (FIXED, Python AND MQL4)

Covered above (superseding the first round's "accepted approximation, not
changed"). `lots_for_risk`/`risk_usd_for_lots` gained
`extra_cost_usd_per_lot` on both the Python (`symbol_spec.py`) and MQL4
(`SymbolSpec.mqh`) sides; both simulators and both EA files now pass the
confirmed 5 USD/lot commission through it. Materially changed real-data
results (see above).

## Section 4.4/4.5/4.6: MQL4 remaining risk items (FIXED structurally, still NOT_RUN)

Same caveat as every MQL4 item in this project: no MetaEditor/MT4 was
available in this session; every fix below is a structural/static-review
correction, not a verified compile or test run. A concrete, short
MetaEditor/terminal test sequence for each of these is in `README.md`'s
"MQL4 test instructions" section.

- **4.4 unprotected-position reconciliation:** previously, if BOTH SL
  application and an immediate close failed, the code only logged a
  warning and relied on the generic account-wide "unknown risk" scan to
  block NEW entries -- nothing ever retried fixing THAT position, and a
  restart lost all memory it existed. Fixed: `Persistence.mqh` now
  persists an emergency state (ticket + originally-intended SL/TP) and
  `OrderExec.mqh`'s new `ReconcileUnprotectedPosition` retries
  protecting/closing it every tick (throttled to avoid hammering the
  trade server or the log), including across a restart, independent of
  whether any daily/total floor has been breached.
- **4.5a portfolio/correlated-group caps in MQL4:** previously a
  documented no-op gap in both EA files ("NOTE: same correlated-group-cap
  gap ... omitted for brevity"). Fixed: `AccountRisk.mqh`'s new
  `NewIdeaWithinRiskCaps` mirrors
  `account_risk.py::new_idea_within_risk_caps` (scanning this EA's own
  MagicNumber-tagged open orders on the two managed symbols, one
  correlated group by construction) and is now called from both EA files'
  entry paths before sending an order.
- **4.5b pending orders in the account-wide scan:** previously skipped
  outright with the excuse "this EA never places pendings" -- this
  follow-up round explicitly rejects that excuse (a MANUAL or FOREIGN
  pending order still carries real activation risk). Fixed:
  `ScanAccountWideRemainingRiskUsd` now also walks pending orders
  (`OP_BUYLIMIT`/`OP_SELLLIMIT`/`OP_BUYSTOP`/`OP_SELLSTOP`), returning
  their worst-case activation-then-SL risk via a new out-parameter, wired
  into both EAs' `NewEntryAllowed` calls instead of a hardcoded `0.0`.
- **4.6 single-controller instance lock:** previously only an
  account/server identity comparison, explicitly NOT an exclusive lock
  (accepts a legitimate restart and a second concurrent instance
  identically). Fixed (partially): `Persistence.mqh`'s new
  `AcquireInstanceLock`/`ReleaseInstanceLock` open a lock file WITHOUT
  `FILE_SHARE_*` flags, held open for the EA's whole lifetime -- a second
  EA instance in the SAME terminal/account fails `OnInit`. Documented
  limitation, not fixed: this cannot stop a second, separate MT4 terminal
  installation (a different data folder/machine) from trading the same
  account unopposed -- that needs a broker/server-side control this
  prototype has no access to.

# Independent Codex review response (2026-09-18, third round -- F1-F5)

An independent review by "Codex" of `docs/FULL_REPORT.md` and
`docs/STRATEGY_RESEARCH_2026-09-18.md` (the two documents produced by the
second follow-up round above) found five further discrepancies in the
Python simulators/accounting, delivered as
`CODEX_FINDINGS_2026-09-18.md`. Per that document's own explicit
instructions and the account owner's forwarding instruction, each finding
was independently reproduced in THIS session with a regression test
written to fail against the pre-fix code first, then fixed, then all 24
(variant x scenario) runs were recomputed. No strategy parameter or risk
limit was changed. Starting point for this round: the commit that closed
the second follow-up round above (the same commit
`docs/STRATEGY_RESEARCH_2026-09-18.md`'s "Reproducibility" section cites,
`2f81dca`, plus every commit since).

## F1: cost-stress scenarios never reached the simulator -- CONFIRMED, FIXED

**Finding:** `scripts/run_experiment_2026-09-18.py`'s `run_one`/`run_all`
computed the scenario's spread only to build a REPORTED cost breakdown
(`spread_price_by_symbol`); the `cfg` object actually passed to every
simulator function never had its `spread_points_hypothetical` field
overridden. C2 and C3 therefore silently ran with C1's spread (10/15
points) for the ACTUAL simulation the whole time -- only the (separately
applied) slippage stress varied.

**Independent reproduction:** patched each simulator entry point with a
spy capturing the `config.spread_points_hypothetical` it actually
received; for C2 it was `{EURUSD: 10.0, GBPUSD: 15.0}` (should be `{20.0,
30.0}`), for C3 the same C1 values (should be `{30.0, 45.0}`) --
confirmed before any fix.

**Fix:** new `apply_scenario_to_config(cfg, scenario)` mutates
`cfg.spread_points_hypothetical` (the field every simulator's
`spread_price()` call actually reads) AND the underlying `cfg.raw` dict
in place, called by `run_all` before `run_one`; the effective post-
override config is hashed into `run_metadata.effective_scenario_config_sha256`
for reproducibility proof. Regression test:
`test_f1_scenario_spread_actually_reaches_the_simulator_config`
(`python/tests/test_codex_findings_2026-09-18.py`).

## F2: per-tick event order leaked future information into entries -- CONFIRMED, FIXED (all 3 simulators)

**Finding:** in the per-tick loop, an already-open position's risk mark
(used to gate a SIMULTANEOUS other-symbol entry) used that position's
CURRENT-MINUTE CLOSE -- a value only knowable after the minute elapses --
and every open position's intrabar SL/TP was resolved BEFORE that same
minute's new entries, meaning risk freed by a later intrabar exit was
usable at the earlier open. This is a broader version of the second
follow-up round's "same-tick causality leak" (section 4.1 above), which
only covered a position opened on the SAME tick as the check; this
finding covers ALL open positions' marks and the ORDER of exit-vs-entry
processing.

**Independent reproduction:** exact repro as specified -- EURUSD BUY
fills at 08:00 from a 07:00 H1 signal, GBPUSD BUY fills at 09:00 from an
08:00 H1 signal, both SL 1.09900/TP 1.12000; varying ONLY EURUSD's
09:00-minute close/high (its open held fixed) flipped GBPUSD's 09:00-open
decision between "Allowed" and "Noraidīta:
CORRELATED_OR_PORTFOLIO_RISK_CAP" -- confirmed before any fix, with the
same GBPUSD decision now identical regardless of EURUSD's close.

**Fix:** every pre-entry decision (risk-view marks, pre-entry equity, the
risk-stop force-close check) now uses a strictly open-based mark
(`_mark_price(symbol, direction, use_close=False)`); intrabar SL/TP for
EVERY open position (not just newly-opened ones) is deferred into a
single unified pass strictly AFTER that tick's entries; the entry
minute's own SL/TP check still runs immediately after entry, unchanged.
Applied identically to `simulator.py` (S1), `simulator_ema_cross.py`
(S2-S6), and `simulator_m30_signal.py` (S7/S8) -- per the task's explicit
instruction to check event order in every simulator used, not do a
narrow fix for the one reproduction case. This is the round's largest
behavioral change: S3's C1 trade count moved from 102 to 147 as a direct
consequence, even though S3 was not part of the original reproduction.
Regression test:
`test_f2_same_minute_close_must_not_change_a_different_symbols_entry_at_the_open`.

## F3: worst-FTMO-day metric measured the wrong quantity -- CONFIRMED, FIXED

**Finding:** `experiment_metrics.py`'s `worst_ftmo_day` compared each
day's LAST equity point to the PREVIOUS day's last point
(end-of-day-to-end-of-day), not the day's LOWEST intraday equity against
that SAME day's own midnight balance (B0) -- the actual FTMO 2-Step daily
floor basis. A day that dipped to exactly `B0-300` intraday and then
recovered to flat by day's end would report `net_change_usd: 0.0`,
hiding a real breach-level move. Also, `working_floor_breach_count` only
counted the simulator's own emitted stop events, with no independent
cross-check.

**Independent reproduction:** synthetic day with equity points [9700,
10000] (B0=10000, no trades) -- `worst_ftmo_day` returned
`net_change_usd: 0.0` despite the equity curve touching exactly the daily
floor (`B0-300 = 9700`) intraday; confirmed before any fix.

**Fix:** new `daily_floor_analysis()` computes, per day, the day's own
recorded B0 (from a new `balance_at_midnight_by_day` ledger populated at
every simulator's rollover event), the day's lowest observed equity, and
the worst move from B0 -- `worst_ftmo_day` now delegates to it.
`full_metrics` also reports `independently_recomputed_floor_breach_days`,
a fresh recomputation straight from the raw equity curve and each day's
own B0, kept alongside (not replacing) the simulator's own
`working_floor_breach_count` for cross-checking. Both read **0 across
all 24 recomputed runs** -- the "no breaches" conclusion is now on firmer
footing than before, since it no longer rests solely on the simulator's
own self-reported stop events. Regression test:
`test_f3_worst_ftmo_day_catches_an_intraday_dip_back_to_flat`.

## F4: monthly table dropped swap and mis-attributed floating P/L -- CONFIRMED, FIXED

**Finding:** `monthly_realized_vs_floating` summed only closed-trade
`net_pnl_usd` per month (swap accrues to a separate account-level ledger
and never appeared in the table at all -- confirmed materiality: S6/C1's
monthly `realized_usd` sum was -97.86 USD against an actual total balance
change of -142.56 USD, a -44.69 USD gap exactly equal to S6's total
swap); floating P/L was attributed only to the SAMPLE's overall last
month (an interior month's own end-of-month floating position, if it
later closed in a later month, was wrongly zeroed for its own month);
and months with zero trades AND zero end-floating vanished from the
output entirely instead of showing zero (e.g. S3's 2026-09 in the
original round's table).

**Independent reproduction:** synthetic two-trade/two-month result with a
still-open position at the first month's boundary that closes in the
second month, plus a zero-activity month in between -- confirmed the
zero-activity month was missing from the output and the first month's own
floating was reported as 0 instead of its real value, before any fix.

**Fix:** `monthly_realized_vs_floating` now includes swap per month (via
`result.swap_ledger`), attributes floating P/L to each month's OWN last
observed equity-curve point, and derives every month in
`_months_between(first_day, last_day)` so zero-activity months appear
with zeros. Output keys renamed/added: `realized_usd` (trade + swap),
`realized_trade_usd`, `realized_swap_usd`, `floating_at_month_end_usd`
(was `floating_at_sample_end_usd`). Regression tests:
`test_f4_monthly_table_includes_swap_and_zero_activity_months`,
`test_f4_interior_month_end_floating_is_not_silently_dropped`.

Secondary observation from the same finding, NOT itself a bug and left
open for a future round: the expectancy/PF metrics currently exclude
swap, and the R-multiple metric's "R" is the REQUESTED fixed 25 USD risk,
not the trade's actual rounded-lot `risk_usd_at_entry` -- the underlying
`r_multiple_net` calculation already correctly uses `risk_usd_at_entry`,
but the reporting/labeling around it should be explicit about which
"R" is being shown wherever expectancy-in-R is quoted. Not changed this
round; flagged as an open item below.

## F5: entry-side commission was never booked until close -- CONFIRMED, FIXED (all 3 simulators)

**Finding:** `order_exec.py`'s `open_position()` created a `Position`
with no commission booked to balance at open; the FULL round-turn
commission (2.50 USD/lot per side, 5.00 USD/lot round-turn -- both
confirmed facts) was deducted only in `_finalize()` when a trade
eventually closed. A still-open position's balance/equity therefore
silently ignored a cost already, in reality, incurred at entry.

**Independent reproduction:** a 0.10-lot position opened with a 5.00
USD/lot round-turn commission rate and never closed left `balance`
exactly at its pre-trade value, with no entry-side commission reflected
anywhere -- confirmed before any fix.

**Fix:** `Position` gained `entry_commission_usd`, computed in
`open_position()` as half the round-turn rate times lots and deducted
from `balance` immediately at open; every simulator's close-path balance
update now adds `trade.position.entry_commission_usd` back when applying
the (unchanged) full round-turn `net_pnl_usd`, so the round-turn is never
double-charged. A still-open position's equity/balance and the day-
rollover B0 snapshot correctly reflect the already-booked entry leg.
Regression test: `test_f5_entry_commission_is_booked_immediately_at_open`
(plus an updated pre-existing test,
`test_swap_accrues_once_per_night_held_and_triples_on_wednesday`, whose
old assertion had itself baked in the pre-fix behavior).

## What this changed, in numbers
